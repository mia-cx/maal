## Problem Statement

The application has outgrown a route-centered architecture. Important product domains now span Svelte pages, route endpoints, server services, DB mappers, stores, and MCP tools, which makes each feature harder to change safely and harder to carve into independently owned surfaces.

The main pain points are:

- Large route and component files are carrying multiple responsibilities at once: orchestration, state machines, form parsing, validation, permissions, persistence, UI rendering, and interaction details.
- Business behavior is duplicated between route handlers and server services. The most concerning duplicated semantics are recipe-to-meal sidecar copying, meal ingredient/instruction replacement, request JSON parsing, active-household authorization, appliance literals, blank-schedule click behavior, and empty recipe/card defaults.
- The frontend is organized mostly by visible page areas, not by stable product/domain modules. This blocks a micro-frontend-style split where domains like plan, menu, household, settings, billing, and MCP can evolve behind explicit contracts.
- Server routes expose too much implementation detail. Several endpoints perform authorization, input decoding, business decisions, and persistence directly instead of acting as thin adapters over domain services.
- The MCP endpoint combines protocol wiring, schema definitions, authorization helpers, tool registry, tool implementations, and result formatting in one module. This makes it hard to add MCP Apps or safely evolve API contracts.
- Test coverage is too sparse for a deep refactor. Existing tests cover ingredient parsing, recipe ranking, taxonomy display, and starter examples, but there are few characterization tests around route/service contracts, MCP tools, schedule interactions, settings flows, household preferences, or copy/update invariants.
- The codebase lacks enforceable module boundaries. The desired maintainability bar is: two semantically duplicated implementations are borderline but acceptable; three are a hard failure and must become a shared abstraction or consciously documented exception.

## Solution

Refactor toward a domain-first, micro-frontend-ready architecture without changing user-visible behavior.

The target shape is:

- Domain modules own their data contracts, application services, route adapters, client adapters, stores, and feature UI.
- SvelteKit routes become thin composition shells that authenticate, call domain entrypoints, and render domain components.
- Cross-domain integration happens through small public APIs instead of direct imports from internal folders.
- Repeated behavior becomes either a shared kernel utility, a domain service, or a generated/declared constant source of truth.
- Large Svelte components are split into controller/state modules plus focused presentational components.
- Server behavior is characterized with tests before each extraction.
- The refactor proceeds by tiny commits. Each commit must leave the app building and the affected behavior working.

Recommended domain boundaries:

1. App shell and session
   - Authenticated app layout, household selection, global nav, current session projection, and cross-domain route guards.
2. Planning
   - Meal plan queries/mutations, schedule state, drag/drop, range loading, check-ins, pool behavior, and schedule UI variants.
3. Menu and recipes
   - Saved recipe CRUD, import, recipe editor, recipe ranking, recipe cards, and recipe-to-meal projections.
4. Household
   - Household profile, members, invites, appliances, locale/timezone/week-start, and household-level preferences.
5. Taxonomy and preferences
   - Units, foods, aliases, effective display preferences, overrides, and taxonomy option loading.
6. Settings
   - Account, security, MFA, email verification, MCP keys, notifications placeholder, and billing entrypoints.
7. Billing
   - Entitlements, subscriptions, checkout, portal, webhook, trial status, and pricing page data.
8. MCP/API
   - Key verification, tool registry, tool schema decoding, tool handlers, result formatting, and API-facing service adapters.
9. Shared kernel
   - Request parsing, pagination, date ranges, response envelopes, invariant helpers, common constants, domain IDs, and small pure utilities.
10. Design system
   - shadcn/ui primitives remain generic. Product components move into domain modules and depend on design system primitives, not the reverse.

The refactor should be implemented as a series of behavior-preserving extractions first, then cleanup/enforcement only after tests prove parity.

## Worktree Setup

Before starting the refactor, create a dedicated worktree:

```bash
git worktree add .worktrees/deep-modularization -b refactor/deep-modularization
cd .worktrees/deep-modularization
```

All commits below should be made in this worktree. Merge back to `main` only after the refactor is complete and tests pass.

## Decision Document

- The refactor is domain-first, not layer-first. Each product domain owns its own application services, UI feature components, and public contract.
- Routes are transport adapters. They should not contain business rules that are also needed by MCP tools, client actions, or other routes.
- MCP is a first-class API surface, not a special route full of one-off handlers. Its tool contracts should be testable independently from the HTTP transport.
- Planning and recipes are separate domains but share an explicit projection service for turning saved recipe content into planned meal content.
- Household settings should compose household, taxonomy, and billing domains instead of owning their internals directly.
- Settings should become a micro-frontend-style category registry so account, security, MCP, billing, and future notification settings can be developed independently.
- Product components may depend on the design system. The design system must not depend on product components.
- Shared abstractions should be created for semantic duplication, not for incidental similarity or ordinary call sequences.
- Three semantically duplicated implementations are a failure mode and must be abstracted or documented as a deliberate exception.
- Characterization tests come before extraction for risky behavior.
- Each commit must preserve behavior and leave the project in a working state.
- Generated or vendor-like UI primitive wrappers are not the primary target of this refactor unless product behavior has leaked into them.
- Schema changes are out of scope unless a refactor exposes an existing schema inconsistency that cannot be safely handled at the service layer.
- Public domain APIs should be stable enough that a future micro-frontend can consume them through a package boundary, route boundary, or RPC boundary.

## Testing Decisions

- Tests should cover external behavior and domain contracts, not implementation details introduced by the refactor.
- Characterization tests should be added before moving risky behavior, especially for recipe-to-meal copying, meal updates, household settings load/actions, settings security flows, MCP tool behavior, and billing status projection.
- Pure helpers should get direct unit tests when they encode policy: pagination, date ranges, parsing, servings normalization, appliance coverage, request body decoding, and MCP input decoding.
- Server application services should be tested through command/query functions with realistic DB rows where practical.
- Route adapters should be tested only for transport concerns: auth failure, missing DB, missing household, invalid body, domain-error mapping, and response shape.
- Svelte component tests should focus on user-visible interactions: schedule slot clicks, protected nested clicks, dialog open/close, editor save/cancel/delete, settings category switching, MFA and MCP key flows.
- Existing prior art includes unit tests for ingredient parsing, taxonomy display, recipe ranking, and starter Svelte component tests. New tests should follow these patterns but replace starter/demo tests with product-domain coverage over time.
- E2E tests should cover at least one happy path per micro-frontend domain: app shell load, plan interaction, menu recipe edit, household settings update, settings dialog security/MCP path, billing status visibility, and MCP smoke behavior if feasible.
- The final refactor should run `pnpm check`, `pnpm test:unit -- --run`, and targeted Playwright tests. Full `pnpm test` should be run before merge if the environment supports browser install.

## Out of Scope

- Rewriting the product UI or changing visual design beyond extraction-related markup movement.
- Replacing SvelteKit, Drizzle, D1, WorkOS, Stripe, Effect Schema, shadcn-svelte, or the MCP SDK.
- Changing database schema or migrations except for unavoidable follow-up issues discovered during refactoring.
- Changing public MCP tool names, argument semantics, or response contracts except through an explicit compatibility/versioning decision.
- Changing auth, billing, or household permission semantics.
- Adding new product features while refactoring.
- Optimizing runtime performance unless a small improvement naturally falls out of duplication removal.
- Refactoring generated/vendor-like UI primitive wrappers unless needed to fix product coupling.
- Solving every test gap before starting. Add tests just ahead of each risky extraction.
